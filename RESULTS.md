The Grafana SRE Performance Monitor streams 1-second interval telemetry directly from Prometheus scrapers running against the microservices cluster on AWS. It focuses strictly on Google SRE Golden Signals and cgroup resource boundaries without audit clutter.

### Telemetry Panel Breakdown & Operational Insights

1. **Real-Time Availability SLO % (`99.9%` Target)**:
   - High-contrast precision gauge tracking rolling successful transaction requests against total ingress volume.
   - Maintained **99.9%** availability throughout peak traffic, momentarily dipping during unmitigated fault intervals before recovering to baseline.
2. **Live Request Throughput (RPS)**:
   - Tracks real-time client traffic demand generated by the concurrent load generator (~25-80 RPS).
   - Serves as the denominator for error rate calculations and verifies system throughput resilience under stress.
3. **Live HTTP 5XX Error Rate %**:
   - Instantaneous percentage of failed requests (`HTTP 500`, `502`, `503`, `504`).
   - Triggers the Blue Team **Health & Uptime Monitor** alert threshold when exceeding 5.0% for longer than 2 evaluation cycles.
4. **Real-Time System State (`HEALTHY` vs. `ACTIVE INCIDENT`)**:
   - State indicator reflecting cluster health. Displays high-contrast green `HEALTHY` under normal parameters and switches to red `ACTIVE INCIDENT` the instant an SLO breach is declared.
5. **Real-Time Latency Profiles (p50, p95, p99)**:
   - Multi-line time series tracking latency percentiles across all active microservices.
   - Demonstrates the sharp latency spike when network delays (`tc netem`) or memory starvation are injected, followed by an immediate collapse back to `<800ms` post-remediation.
6. **Live Ingress RPS vs. 5XX Server Errors**:
   - Direct dual-axis visual correlation between incoming traffic volume (blue line) and server fault responses (red filled area), allowing SREs to distinguish capacity exhaustion from functional failure.
7. **Microservice Memory Usage vs. Cgroup Ceiling (MB)**:
   - Resident memory consumption for each microservice plotted directly against the hard **256MB cgroup limit**.
   - Visualizes physical memory leaks approaching the ceiling before the automated recovery agent purges buffers or restarts containers prior to kernel OOM kills.
8. **Service Traffic Ingress Share**:
   - Donut breakdown illustrating request distribution across microservices (`api-gw`, `order-service`, `payment-service`, `inventory-service`, `frontend`).

## 2. Autonomous Agent Security Audit Stream

All commands executed by both offensive and defensive agents are captured in an immutable, real-time audit ledger streamed to AWS CloudWatch Logs under `/sre/autonomous-agent-audit`.

<p align="center">
  <img src="docs/images/cloudwatch_agent_command_audit.png" alt="AWS CloudWatch Agent Command Log Audit Dashboard" width="950" />
</p>
<p align="center"><b>Figure 2: AWS CloudWatch Agent-Command-Log Dashboard (Dual-Pane Red vs. Blue Team Command Logs)</b></p>

### Audit Structure & Security Boundary Analysis

- **Dual-Pane Separation of Intent**:
  - **Left Pane (Red Team: Injected Commands & Outputs)**: Captures exact chaos injection commands, target container names, injected fault parameters (e.g., Linux kernel `tc netem delay 250ms`, Redis connection pool exhaustion, synthetic heap allocations), and raw execution return codes.
  - **Right Pane (Blue Team: Remediation Commands & Outputs)**: Records automated runbook invocations (e.g., container restarts, cgroup memory purge, downstream latency parameter resets, network rule flushes), execution latency, and verification exit codes.
- **Unified Security Audit Ledger**:
  - The lower pane aggregates both streams into a chronologically ordered, tamper-evident timeline.
  - Ensures complete forensic accountability: every automated remediation action is cryptographically tied to the preceding diagnostic prompt and LLM reasoning chain.

## 5. Engineering Takeaways & Reliability Conclusions

1. **Autonomous Closed-Loop SRE is Production-Viable**:
   - By marrying real-time streaming metrics (Prometheus/Grafana) with an LLM diagnostic engine running Claude 3.7 Sonnet with Extended Thinking, incidents that typically take 15–45 minutes of human on-call triage are diagnosed and resolved in **under 60 seconds**.
2. **Clear Separation of Observability Concerns**:
   - Dedicating Grafana strictly to operational golden signals and CloudWatch strictly to security auditing and attack vectors prevents alert fatigue and keeps operators focused during active incidents.
3. **Safe Multi-Agent Coexistence**:
   - Running offensive and defensive agents within a hardened, resource-constrained Kubernetes sandbox namespace (`sre-agent-sandbox`) ensures chaos testing never threatens host node stability or unauthorized network egress.
